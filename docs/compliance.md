## 最终发布结论：**有条件发布（Conditional Release）**

在「可发布 / **有条件发布** / 不建议发布」三项结论中，Parallaxe box 的审慎结论为：**有条件发布**。

含义：**由本项目独立原创编写、离线可运行且默认零发包的只读诊断工具可以准备开源发布（如 GitHub Release）**；但这**不是** GitHub 的预批准，**不是**对 107 个 Google 目标或 28 个对照目标的自动访问授权，也不是对任何国家/地区运营合法性的法律背书。

### 发布必须满足的前置条件
1. **默认空许可不变**：内置 `assets/targets.toml` 的 `admission.grants` 保持为空、内置目标 `allow_online = false`；未逐址复核条款与许可的目标绝不在默认或 `--full` 模式下自动联网。
2. **仅按白名单打包**：只发布原创代码、合规资产与净化文档，严格排除 `sessions/`、`refs/archives/`、`refs/design-ui/`（含 GPL-3.0 与无 LICENSE 参考仓库）、`.workbuddy/` 及一切私有过程记录。
3. **脱敏与零凭据扫描通过**：源码、资产、fixture、测试、截图与文档零真实公网 IP、零 Cookie、零凭据/Token、零真实订阅链接、零未授权第三方完整响应。
4. **合规文案与声明就位**：README、GUI 首屏、自定义导入（`liability-v1` 双勾选与 F3 弹窗）及本文档清晰陈述用途边界、免责声明与禁止用途，绝不使用「解锁/洗白/绕过限制」等营销表述。
5. **维护人终审签字**：发行前由维护人再次复核目标平台最新条款与 [release-checklist.md](release-checklist.md) 中的人工待签项。

## 逐条回答规格 §12 的 7 个核心合规问题

### 问题 1：匿名 GET、公开页面解析、地区观察和本机规则生成是否涉及 GitHub 禁止类别？

对照 GitHub Terms of Service（查阅版标注生效日 2026-04-27）与 GitHub Acceptable Use Policies（AUP，2026-11-21 查阅，均为 `OFFICIAL_DOC`）：
- **平台边界**：GitHub ToS C / AUP §1 要求遵守适用法、知识产权、制裁与出口管制，不得设计恶意规避工具；ToS D/F 与 AUP §3 要求上传者对代码、素材与数据权属负责；AUP §2、§4–5 禁止欺诈、虚假账号、滥用自动化、未授权访问与服务干扰；ToS H 与 AUP §7–9 限制 API 与数据滥用。
- **对本项目的判断**：低频、单次、有预算的匿名只读诊断工具本身，以及纯本地内存规则预览，不属于欺诈、恶意软件或未授权入侵类别；但**不得**利用 GitHub Actions 作为出口池去批量探测外部目标，**不得**附带借来的第三方抓取数据集或私有凭据。
- **三道不同的门**：平台托管政策、目标服务使用条款、使用者当地法律是三道独立的门。GitHub 允许托管不代表目标网站允许自动抓页，更不代表在所有司法辖区可无限制使用。

### 问题 2：同类项目为何能够公开存在，哪些行为与本项目不同？

同类公开仓库（如 `lmc999/RegionRestrictionCheck`、`xykt/IPQuality`、`tombcato/clash-ip-checker` 等）的公开提交与发布历史，只能佐证「有人在 GitHub 上公开托管过网络检测工具」，**既不是平台批准，也不证明其历史做法合法或可复制**。

本项目与它们的核心差异：
- **不继承高风险行为**：不复用浏览器或第三方 Cookie，不嵌入第三方账号/订阅凭据，不批量遍历代理订阅或自动切换代理组，不调用外部黑盒 IP 评分 API 上传用户出口信息；
- **尊重目标服务条款**：
  - 依据 Google 条款与 Search `machine-generated traffic` 政策，不自动提交搜索词、不抓取排名；
  - 依据 YouTube 条款（Permissions and Restrictions 第 2–3 项），未获适用事前书面许可时，不上线抓取首页/Music/Premium 页面；
  - 依据 Netflix 使用条款 §1.8，不抓片库、不播放、不测 DRM（目录仅登记公开条款页作资料参考）；
- **默认零发包**：内置目录 `admission.grants = []`，先守住授权边界，不以「HTTP 200 或 robots 未禁止」冒充许可。

### 问题 3：代理规则、hosts 和防火墙在什么前提下属于本机网络管理？

仅在以下前提**全部满足**时，相关规则预览或未来受控导出才属于合理的本机网络管理：
1. **管理权前提**：只针对使用者拥有合法管理权的本机设备，只作用于本机自身出站流量，不影响他人网络、不干扰或操纵远端服务；
2. **生成 ≠ 应用**：当前版本 Guard 为纯只读预览（`applied = false`、`rules_written = 0`），无 `--apply`、不改用户代理配置、不碰 hosts、不改防火墙；
3. **保护关键基础设施**：登录、OAuth、付款、证书校验、Play 下载与共享 CDN 永久受保护，绝不按 IP/ASN 封禁；
4. **不越权**：拥有本机网络管理权，**绝不等于**取得未经许可自动探测远端服务的权利。

### 问题 4：「解除地区限制」「解锁」等表述为什么不应出现在 README？

1. **与事实不符**：本软件只做只读事实观测与本机影响闭包预览，没有任何修改远端地区判定、改变账号国家或解除限制的功能；宣称「解锁」属于虚假夸大。
2. **触发平台与目标条款红线**：「解锁」「洗白」「绕过限制」「规避风控」直接指向绕过技术保护措施（TPM）、地区许可或付费/DRM 边界，极易触发 GitHub AUP 与目标服务条款的违规认定。
3. **正确定位表述**：README 与首屏统一采用：**「诊断出口地区判定，辅助选择线路；本工具逐服务展示匿名证据，不选择或切换线路。」**

### 问题 5：MIT、Apache-2.0、AGPL-3.0 的取舍与第三方代码复用边界？

- **本项目原创代码许可**：采用 **`MIT OR Apache-2.0`** 双重许可（与 Rust 生态主流一致）。`Apache-2.0` 提供明确专利授权与 `NOTICE` 保留机制，`MIT` 简短宽松、易于下游兼容。
- **拒绝 GPL / AGPL 传染**：`AGPL-3.0` 与 `GPL-3.0` 具有强互惠传染义务，绝不能按 MIT/Apache 条件混入本项目源码。
- **第三方依赖与参考库边界**：
  - `Cargo.lock` 全部 488 个外部依赖经核查**无任何 GPL/AGPL 依赖**（唯一含多许可 `MIT OR Apache-2.0 OR LGPL-2.1-or-later` 的 `r-efi` 在本项目按 `MIT OR Apache-2.0` 选用；`epaint_default_fonts` 的 `OFL-1.1 / UFL-1.0` 字体声明与 `webpki-roots` 的 `CDLA-Permissive-2.0` 已完整列明于 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)）。
  - 开发期本地参考库 `refs/design-ui/` 中包含 **Axolotl Launcher（GPL-3.0）** 与 **System Monitor（无 LICENSE）**：严格执行**只看视觉/布局思路、零代码/CSS/素材复制**，且整个 `refs/` 目录排除在发行白名单之外。
- **开源许可与禁止用途的关系**：依据开源定义（OSD §6），README 中的使用规范与免责说明**不能单方面缩减**已经按标准 MIT / Apache-2.0 授出的开源权利；若商业化托管服务需要强制执行禁止用途 EULA，须针对托管服务或独立商业分发另行制定协议。
